# ADR-0001：用户登录采用「服务端会话 + Cookie」而非 JWT

- 状态：**已采纳**（默认方案；用户尚未拍板，但本项目已按此实现并保留切换路径）
- 日期：2026-10-20
- 关联实现：`user_auth.py`
- 关联契约：`docs/user-login-api-contract.md`
- 决策人：项目负责人（未拍板时的默认决策，见下方「若不认同」）

---

## 1. 背景

要给控制台加「用户登录」。目前：

- 控制台是 `openai_proxy.py` 内嵌的同源单页应用（`CONSOLE_HTML`），所有请求都是 `fetch(API + '/api/...')` 的同源相对调用；
- 已有的是 **API Key 鉴权**（`off` / `partial` / `strict` 三档，`auth.json`），面向 OpenAI SDK 这类**机器客户端**；
- 本次要加的是**人（浏览器）登录**：账号、口令、会话、管理员角色；
- 需求方明确表示「JWT 还是 session 还没想好」。

因此本 ADR 的作用不是二选一地拍脑袋，而是：**在需求方没拍板时先给出一个可辩护的默认答案，并把「改判」的成本压到最低。**

## 2. 决策

**采用服务端会话（不透明随机 token）+ Cookie（`tap_sid`，HttpOnly、SameSite=Lax）。**

登录会话表存于进程内存（`LoginSessionStore`），账号库存于 `users.json`（口令用 PBKDF2-HMAC-SHA256 加盐）。

> 术语：本仓库里 "session" 专指 **super-agent 会话**（`create_session` / `/api/sessions`），
> 与「登录会话」同名不同物。本文与代码一律用 **登录会话 / login session** 指代后者。

**同时把「凭据形态」隔离在接口之后**：路由层只认 `AuthManager` 的 `login() / authenticate() / logout()`，不认「Cookie 里的那一串东西到底怎么来的」。日后若改用 JWT，只需新增一个同接口的 `JwtProvider` 并替换 `AuthManager` 内部实现，**路由、前端、契约一律不动**。

## 3. 为什么现在不选 JWT

| 维度 | 服务端会话（本决策） | JWT |
|------|--------------------|-----|
| 前端契合度 | 同源浏览器 UI，Cookie 免手动携带、无需 localStorage | 通常要存 localStorage 并给每个 `fetch` 手工加 `Authorization` 头，**改动面覆盖控制台所有 12 处 fetch** |
| 泄露面 | HttpOnly Cookie 不受 XSS 窃取；会话 id 是 256 位随机串，泄露面 = 会话本身 | 令牌在 localStorage，任意 XSS 即可窃取；且 JWT 默认在过期前一直有效 |
| 吊销 | 登出 / 停用账号 / 改口令**立即生效**（删一条会话记录） | 无状态令牌照登出；要即时吊销就得再维护一份黑名单 —— 那等于又做了会话表 |
| 依赖约束 | 本项目**零第三方依赖**（纯标准库，见 README「技术细节」） | 手写 HS256 本身不难，但要额外承担 base64url / `alg=none` 混淆 / 时钟偏移 / 密钥轮换等一整套正确性负担 |
| 部署形态 | 单进程本地代理（Windows 任务计划 / macOS launchd），内存会话够用 | 无状态的优势要到多节点水平扩展才兑现，而本项目目前是单机单进程 |
| 迁移成本 | — | 若日后真要 JWT：新增 1 个 provider 类 + 改 1 处工厂方法，契约不变 |

**决定性理由**：JWT 的核心卖点（无状态、可离线校验、跨服务传递）在本项目当前形态下**没有一个能兑现**；而它的成本（前端全量改造 + 吊销难题 + 自行实现签名）是**立即要付**的。控制台是给人用的浏览器界面，服务端会话正是它的原生形态。

## 4. 后果

**正面**

- 控制台登录页、用户管理页的实现量最小（Cookie 自动携带，前端零改造即可拿到会话）。
- 登出、停用账号、踢下线都是 O(1) 内存操作，语义干净。
- 与既有「API Key 管机器、用户登录管人」的分层天然契合：数据面 `/v1/*` 继续用 Key，管理面 `/api/*` 用会话。

**负面（明确接受）**

- 会话不跨进程：代理重启后所有人需重新登录。可接受（本地单进程服务），且更安全。
- 会话不跨节点：若未来要多实例，需要把 `LoginSessionStore` 换成共享存储（Redis/DB）—— 这是它独立成类的原因，替换成本局限在一个类内。
- 管理面多了一层 cookie 依赖，`openai_proxy_manager.py` 这类 CLI 客户端在 `required` 模式下需要先登录（已列入 Lane C 的改造项）。

## 5. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 忘记登录导致机器人/CLI 被打断 | 三档模式 `off → optional → required` 灰度；`optional` 保留本机放行，回滚只需改一个配置项 |
| CSRF（Cookie 会话天然 susceptible） | 变更类请求强制 `X-CSRF-Token` 双提交校验（服务端会话内生成），配合 `SameSite=Lax` + `HttpOnly` |
| 撞库 / 暴力破解 | 按「用户名 + 来源 IP」失败计数，5 次失败锁定 60 秒；错误文案不区分「用户不存在」与「口令错误」，避免用户枚举 |
| 口令库泄露 | 只存 PBKDF2-HMAC-SHA256(210k 次) 盐哈希，不存明文/可逆密文；`users.json` 加入 `.gitignore` |
| 管理员误删唯一管理员 | 管理操作要求 `admin` 角色；禁止删除/降级最后一个管理员（实现细节见契约「管理操作约束」） |

## 6. 若不认同：改用 JWT 的具体步骤

预期工作量 **半天以内**，且不影响前端与路由：

1. 在 `user_auth.py` 新增 `class JwtProvider`，实现 `issue(user) / resolve(token) / revoke(token)`，用标准库 `hmac` + `hashlib` 做 HS256；
2. `AuthManager` 内部把 `LoginSessionStore` 换成 `JwtProvider`（其余方法签名不动）；
3. 凭据载体从 Cookie 改为 `Authorization: Bearer <jwt>`（或仍用 Cookie，两种都可）；
4. 补充「密钥管理」：签名密钥存 `users.json` 同级配置文件，支持轮换（`kid` 头）；
5. **不变的部分**：所有 `/api/auth/*`、`/api/users*` 端点、错误码、角色模型、`user_auth.py` 的其余 API、前端交互。
