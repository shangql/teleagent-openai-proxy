## 1. 对 PRD 结论的最强反面论述（steelman）

PRD 推荐"服务端会话"，其最强反驳不是"JWT 更现代"，而是下面三条：

### S-1 反方案 B 的最强版本：JWT 的真正优势是**可携带**，不是"无状态"

PRD 否决 JWT 的理由之一是"无法即时吊销"。但在本仓库，撤销诉求其实很弱：

- 会话要撤销的只有**控制台人类**，而控制台本身只在本机/LAN 使用；
- 现有 `tap-` API Key 已经是可撤销的机器凭证（`openai_proxy.py:294-309` 有 `status`/`expire_at`），**机器侧撤销能力并不缺**；
- 真正的诉求是"看得出操作人是谁"，而不是"秒级踢人"。

在这个诉求下，JWT 的"自包含、可携带（可放 header、可跨主机）"是真优势：**Cookie 是 host-scoped 的**（见 T-2），而 JWT 可以放在 `Authorization` 头里被任意前端携带。
→ 反驳 PRD 的推论：PRD 用"撤销"当主否决理由，但撤销在本场景**不是主要矛盾**；JWT 在"可携带"上是净胜。PRD 的结论（选 session）仍然正确，但**否决理由排错了序**，应改为：真正决定性的是 **P1 零依赖下自造 HS256 的密码学风险** + **与既有 `tap-` 体系职责重叠**。

### S-2 反方案 C 的最强版本：人为什么不能像机器一样拿 key？

PRD 用"key 是机器凭证"否定方案 C。但这个区分在本仓库里其实很薄：

- `tap-` key 有 `name`、`status`、`expire_at`、`allowed_models`，已经是一个**带元数据的凭证实体**；
- 所谓"账号"与"key"的差别，在单机代理上只剩"口令哈希 + 角色"两点。

反方论点：**要实现的不是"账号系统"，而是"一个人一个可撤销凭证 + 审计"**。如果照 PRD 做，仓库里会同时存在 `auth.json`（机器凭证）和 `auth_users.json`（人类凭证）两套凭证存储 —— **这是新的双重真相源**，而 PRD 原则 P4 恰恰要求"一处判定"（虽然 P4 讲的是判定点，不是存储）。
→ 结论：PRD 的取舍可接受，但**必须显式承认"双凭证存储"是有意为之**，并写清二者职责边界，否则将来一定有人把两者混用。

### S-3 反面论述：登录可能根本不是正确的主线

Contrarian 在访谈阶段已提出（真问题是暴露面）。Architect 认为这条在 PRD 里**没有被真正吸收**：PRD 把 `ODL-8`（监听地址）推给用户，自己只实现登录。若实例继续跑 `0.0.0.0`，新增的登录只保护了 `/console` 与非本机 `/api/*`——**本机免鉴权路径依然完全开放**（`openai_proxy.py:353`），而 `/api/logs` 会暴露完整请求内容。
→ 结论：**登录是纵深防御的一层，不是主控制**。PRD 应把"监听地址"从"用户偏好"提升为**发布检查清单的一等公民**，并在 PRD §5 风险表中新增一条"即使启用登录，暴露面未收窄时风险仍然显著"。

## 2. 至少一处真实取舍张力

**张力：撤销能力 vs. 泄露面 —— 两个方案各赢一半。**

| | session | JWT |
| --- | --- | --- |
| 撤销（登出即失效） | ✅ O(1)，服务端删条目 | ❌ 需 denylist，denylist 即状态 → 优势归零 |
| 令牌泄露后的影响面 | 仅服务端内存，磁盘无痕；重启即失效 | 有效期内任何持有者可用（除非加 denylist） |
| 泄露后的可见性 | 需服务端日志 | 同 |
| 携带性（跨 host / 放 header） | ❌ Cookie host-scoped | ✅ |

PRD 只在"撤销"轴上比较，**未在"泄露面"与"携带性"轴上比较**。把两轴都摆出来后，选择 session 的真正理由是：
**泄露面（令牌不落盘、重启即失效）在本场景权重高于携带性**，因为携带性的需求（跨 host 前端）在单控制台场景下并不存在——而一旦真的需要跨 host，说明部署形态已经变了，那时应该重新评估（写进 ODL-2 的证伪条件）。

## 3. 有条件时的综合方案（Architect 建议的修订方向）

1. **保留 session 方案**，但把 PRD §0 的否决理由重排：主理由 = 零依赖下不手写 HS256；次理由 = 撤销；再次 = 与 `tap-` 职责重叠。**撤销降级为"加分项"而非"主否决理由"**（因为 S-1 证明撤销在本场景权重不高）。
2. **采纳"双凭证存储"但显式分工**：`auth_users.json` 只管人（口令哈希、角色、登审计），`auth.json` 只管机器（`tap-` key）。二者在 `_auth_check` 汇成同一个判定入口（P4 成立），但**存储层分开**（因为生命周期与轮换策略完全不同）。
3. **发布检查清单把"监听地址"提升为一等公民**，与登录同权重。
4. **修正 P3 违反（见 §4）**。

## 4. 违反原则之处（`--deliberate` 必填）

| # | 违反的原则 | PRD 原文位置 | 说明 | 证据 |
| --- | --- | --- | --- | --- |
| **V-1** | **P3 凭据不落明文** | PRD §0 原则 P3 + 规格 S3「引导时打印一次性口令」 | 计划任务把 stdout 重定向到文件：`$stdout = Join-Path $LogDir "proxy.out.log"`，`$stderr = ...proxy.err.log`（`install-scheduled-task.ps1:62-63`），且 runner 直接执行代理（`:69-73`）。因此"打印到 stdout"= **明文口令落盘到 `%LOCALAPPDATA%\TeleAgentOpenAIProxy\proxy.out.log`**，P3 被自己打破 | `install-scheduled-task.ps1:62-73` |
| **V-2** | **P5 可回滚**（弱违反） | PRD §0 原则 P5 与 AC-14 | `--no-login` 只在**启动参数**里；服务已在运行时无法一键关登录。另外若已存在 `auth_users.json` 但用户忘了口令，回退需要删文件——**删文件是破坏性动作**，README 未给出安全的一键回退 | PRD §6 AC-14 |

## 5. 未被覆盖的张力（须在 PRD 补齐）

| # | 张力 | 建议处置 |
| --- | --- | --- |
| **T-1** | **CSRF 面**：`SameSite=Lax` 的 Cookie 在**跨站顶层 GET 导航**时仍会带上；`POST /api/default-model`、`/api/permission/reply` 等是状态变更端点 | 状态变更端点要求 `Content-Type: application/json`（跨站表单无法伪造该 Content-Type，且会触发预检）；登出端点无害可豁免。在测试规格补一条 CSRF 断言 |
| **T-2** | **Cookie host-scoped**：用户在 `http://127.0.0.1:8088` 登录后，访问 `http://192.168.x.x:8088` **不会带 Cookie**（浏览器规则），用户会误以为"登录坏了" | README 明写；登录页提示当前访问地址；不引入跨 host 方案（这正是 T-2 支持 session 而非 JWT 的反向证据） |
| **T-3** | **同源限制**：`/api/*` 允许 API Key，`/console` 要求 session，两者鉴权材料不同 → 前端若未来要从页面里调 API，需带 key | 明确边界：`/v1` 用 key，`/api` 用 session 或 key，页面内调用一律走 session |

## 6. 复审要求

修订后必须逐条回应：

- V-1 → 引导流程改为**不由服务生成/打印口令**（建议：口令由运维用 CLI 显式设置；无账号时代理处于"未启用登录"的自举态）。
- V-2 → 给出**运行期也可用**的无损回退（如 `--no-login` 之外，提供"改一个配置字段"级别的回退），并在 README 写清恢复步骤。
- T-1 → 状态变更端点的 JSON Content-Type 要求 + 对应测试用例。
- T-2/T-3 → PRD 风险表与 README 补写。
- S-1 → PRD §0 的否决理由重排（撤销降级为加分项）。
- S-3 → 发布检查清单中"监听地址"升为一等公民。

**结论：REVISE**。修订后需重跑 Architect 复审与 Critic 复评（不得由同一份 r1 直接放行）。
